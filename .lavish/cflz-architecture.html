Cloudflare Landing Zones

A framework for running a multi-account, multi-zone Cloudflare estate as code. It is not a collection of Terraform examples — it is an opinionated operating model: where configuration lives, how state is partitioned, which credential is allowed to touch what, and what a human has to approve before anything changes at the edge.

1 · The mental model

A landing zone is the agreed baseline an environment lands in before any workload arrives — identity, topology, security posture and guardrails decided once and enforced everywhere. CFLZ borrows the structure of Azure Landing Zones and the Microsoft Cloud Adoption Framework and applies it to Cloudflare's edge. Three ideas carry the whole design.

01

GitOps over click-ops

Terraform never runs on a workstation. Credentials and state keys live only in GitHub Environments. The dashboard becomes a read surface; the repository is the source of truth, and anything created by hand is detectable because managed resources carry a managed-by tag.

02

Logic separated from configuration

.tf files are customer-agnostic and identical across every tenant. Everything tenant-specific — account IDs, domains, IP ranges, rules — is data in .tfvars. Onboarding a zone is a config edit, not a code change.

03

Decoupled state per layer

Each Cloudflare product area is its own root module with its own state file and its own scoped API token. A WAF apply cannot propose destroying a zone, because zones are not in its state and its token cannot edit them.

Platform Landing Zone

Account-level foundation: RBAC and audit, Zero Trust identity, device posture, egress filtering, tunnels, Magic WAN, and central Logpush streams to a SIEM or R2. It also owns the vending process — the repeatable way a new domain is onboarded already inheriting the security baseline.

Application Landing Zone

Per-zone and per-workload scope: DNS records, WAF custom rules and rate limiting, cache and transform rules, load balancing, Authenticated Origin Pulls, R2 buckets, and Workers with their KV, D1 and queues. Teams get domain autonomy inside platform guardrails.

2 · How the repository is shaped

Three directories, three different jobs. The question this figure answers: if I am onboarding a customer, which files do I touch?

Upstream template, downstream tenants

This repository is the upstream template. A production deployment is a fork into the customer's own GitHub organisation, with their own R2 state bucket and their own scoped tokens. Modules live here for development convenience, but a real tenant points each layer at a tagged external module repository, so a commit on main cannot reach live infrastructure until someone bumps a version deliberately.

Config precedence

  1. layers/<layer>/defaults.auto.tfvars — platform baseline, auto-loaded, customer-agnostic.
  2. accounts/<account>/*.tfvars — passed with -var-file, overrides defaults.
  3. local.auto.tfvars — operator experiments, gitignored.
-var-file does not merge maps — the last file defining a variable wins wholesale. So account config is partitioned by variable: no two files in an account tree assign the same top-level variable. tf-varfiles.sh relies on that to work out which files a layer takes.

The same idea in four files

Follow one DNS record from configuration through to the Cloudflare resource. Nothing customer-specific appears outside the first two files.

config deployment/accounts/account_a/zones.tfvars — identity only: logical key → domain. Passed to every layer.
config deployment/accounts/account_a/dns.tfvars — records keyed by the same logical keys.
layer deployment/layers/dns/zone_lookup.tf + dns.tf — resolves the zone by name at plan time, then fans out over the module.
module modules/dns_records/main.tf — takes a zone_id, not a domain, so it never owns the zone.
Note the lifecycle { precondition } block. Every layer carries a preflight.tf and every module validates its own inputs, so a config mistake — an orphaned key, a duplicate record, an out-of-range tag value — fails at plan time with a sentence explaining it, rather than applying cleanly against nothing.

3 · State segmentation and blast radius

The question this figure answers: what is the worst a single bad apply can do? In Cloudflare the answer matters more than in most clouds, because deleting a zone takes every DNS record in it.

No cross-state reads

Consumer layers never use terraform_remote_state. They resolve a zone key to a zone ID with data "cloudflare_zone" filtered by name and account. States stay fully decoupled, so any layer can be re-initialised or migrated alone — the trade is that consumer layers need the Cloudflare API reachable at plan time.

Locking without DynamoDB

R2 has no lock-table equivalent, so concurrent applies on one key could corrupt it. use_lockfile = true uses S3 conditional writes, which R2 supports. That is why every layer pins required_version >= 1.11.0: on older Terraform the argument is not understood, and the failure mode is an unlocked apply rather than an error. Pipeline concurrency groups serialise per state key as a second defence.

Backend committed commented-out

The backend "s3" block ships commented out so CI can run terraform init -backend=false offline with no credentials. The runner injects bucket, key and endpoint at init time, so nothing account-specific is ever committed.

4 · Execution order is derived, not declared

Layer directories carry no numeric prefixes. Order comes from real infrastructure dependencies, and tf-matrix.sh reads those out of the Terraform source. The question this figure answers: why does adding a layer not require editing the pipeline?

Why zerotrust is an exception. Access applications are addressed by hostname, so the zone and its DNS record must exist — but the layer never reads a zone data source, so nothing in the Terraform expresses the dependency. It is listed explicitly, and the script refuses to start if that list names a directory that does not exist, or a layer that also calls zone_base.
What the script emits. matrix (one job per account-layer pair), by_layer, apply_order as a list of tiers, and per-tier subsets with tierN_any flags. On a PR it narrows by changed files — touching modules/zone_base/ selects every layer that calls it, for every account.

Rate limiting is load-bearing, not a nicety

The Cloudflare provider paced itself in 4.x via rps, retries and backoff arguments. The 5.x rewrite dropped all four and never replaced them, so a 5.x provider has no rate limiting and no 429 retry (provider issue #5505). At a few hundred zones a single plan is thousands of GETs, and unpaced it dies partway through with 429 code 971. Plans on zones are therefore slow by design: a refresh of n resources cannot finish faster than n / api_rps seconds. Raising api_rps above 4.0 does not speed it up, it makes it fail.

Tagging, until the provider catches up

Cloudflare's Tagging API is in public beta and the provider has no tagging resource (none as of 5.24.0), so Terraform decides the tags and a script writes them. Four layers — zones, zerotrust, r2, workers — validate tags.tfvars at plan time and output the full tag set with IDs; the apply job uploads that as a manifest, and a separate tag-only job reconciles it. Every managed resource carries managed-by and layer, which tfvars cannot override — so filtering on tag=!managed-by finds anything created by hand. DNS records are deliberately untagged: the beta caps an account at 10,000 tags.

6 · Credentials and environments

The access model is the architecture. One GitHub Environment per account per layer means a credential that can rewrite WAF rules is physically unable to touch DNS, and only account_governance can grant administrative access.

<account>-plan

One per account. Read-only Cloudflare token plus any TF_VAR_* secrets a plan needs. No reviewer, any branch — a plan cannot change anything.

<account>-<layer>-apply

One per layer. Holds that layer's write token behind a required reviewer, restricted to main. Created by bootstrap-environments.sh.

<account>-tags-apply

Tag-only token. No reviewer by design: it writes only what an already-approved apply output, and has no plan of its own to show. Still main-only.

What is committed, and what never is

Account IDs, domain names, IP ranges and routing topologies live in .tfvars — operational configuration, not secret material, protected by private-repo access control. .gitignore is default-deny for *.tfvars with explicit allow-listing, and re-denies terraform.tfvars, local.auto.tfvars and *.local.tfvars.

Secrets arrive only as environment variables: the Cloudflare token, the R2 state keys, and a handful of TF_VAR_* maps — IdP client secrets, Magic WAN pre-shared keys, Logpush destinations, device-posture integration secrets, origin-pull private keys.

Private modules without a PAT

GITHUB_TOKEN is scoped to this repository alone, so terraform init against a private modules repo would fall through to interactive git auth. The modules-auth composite action mints a GitHub App installation token per run: roughly one hour, read-only, scoped to that one repository, revoked in a post step. Nothing is tied to a leaver and nothing expires silently. It even shape-checks the PEM, because a malformed key otherwise fails deep inside Node's WebCrypto with no hint that the secret is the problem.

7 · Where CFLZ departs from Cloudflare's own guidance

Cloudflare's Terraform best-practice guidance recommends organising by account / zone / product directories and advises teams to "avoid modules (or use them sparingly)". CFLZ deliberately does neither — worth understanding before you judge the layout.

QuestionCloudflare guidanceCFLZ, and why
Modules Avoid, or use sparingly — shared monolithic modules hide security behaviour behind ternaries and unpinned local paths, and an internal change can unexpectedly recreate dependent resources. Use them, but one repository per module with immutable SemVer tags. A breaking input change cannot reach a tenant without an explicit tag bump, and each product area gets its own commit history for audit.
Zone layout One directory per zone, each with its own duplicated .tf files. Code lives once per product layer; zones are for_each entries in tfvars. At 50+ zones the directory model means a provider bump edits hundreds of files.
State Implicitly one state per zone directory. One state per account × layer. Zone deletion — the most destructive Cloudflare failure mode — is isolated to the zones layer alone.
Cross-layer references Not addressed. Never terraform_remote_state; always a plan-time data-source lookup. No inter-state coupling, no pipeline locking, layers migrate independently.
Multiple accounts Not addressed. One run per account, never a for_each over accounts — a provider block carries one token and Terraform cannot take a dynamic provider alias in a for_each module. That constraint is turned into the isolation guarantee.
Limitation, stated by the project itself. Coverage is not exhaustive — a given deployment may need new variables or resources added to the .tf files. Before a commit the maintainer formats and validates the Terraform and runs the offline guardrail tests, and tests deployment where possible, but not every edge case or provider update is covered. There is no feature timeline; contributions go through CONTRIBUTING.md.

8 · Making a change

Adding a zone — config only

  • Branch. Never commit to main.
  • Add the logical key → domain to accounts/<account>/zones.tfvars.
  • Add its settings to zone_config.tfvars and its records to dns.tfvars, under the same key.
  • Open a PR. ci.yml narrows to the affected layers and runs fmt, lint, validate and an offline plan.
  • Merge, then dispatch terraform-apply. Tier 2 creates the zone; tier 3 fills it.

Logical keys are permanent identity. Renaming one destroys and recreates the resource. Keys are scoped per account: primary in account_a is unrelated to primary in account_b.

House rules for changing the Terraform

1Keep .tf files customer-agnostic. Never hardcode tenant values outside .tfvars.
2Change .tf upstream first, then propagate downstream to tenant repos — not the other way round.
3Never run terraform init locally; state is remote and pipeline-managed.
4A new module means updating the workflows in .github/workflows.
5Comments explain the why, not the what. Everything conforms to terraform fmt.
6Conventional Commits, aligned to SemVer: fix: → patch, feat: → minor, feat!: or BREAKING CHANGE: → major.
